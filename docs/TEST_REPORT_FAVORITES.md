# 收藏持久化与跨设备恢复测试报告

## 范围

- 游客收藏使用浏览器本地缓存，首屏可从缓存快速恢复。
- 登录账户使用现有稳定 `roomUserId` 关联服务端 Redis 收藏。
- 游客登录后将本地收藏幂等合并到账户收藏。
- 会话登录、退出和切换后重新读取当前身份的收藏。
- 收藏按 `音乐源:歌曲ID` 去重，服务端返回结果覆盖账户本地缓存。
- 房间收藏列表、心形按钮、批量导入与账户收藏使用同一套客户端同步逻辑。

## 数据与权限约束

- 收藏 Redis Key 保持为 `openmusic:favorites:<roomUserId>`。
- 不新增第二套 `accountId` 收藏存储。
- Socket 收藏事件不接受客户端指定的目标用户身份。
- 游客缓存与账户缓存按身份隔离，账户切换时不得串读。
- 游客缓存导入到账户后，以服务端合并结果作为最终状态。

## 提交 2 同步状态实现

- 客户端状态持久化在 `openmusic:favorites-sync:v1:guest`，支持 `pending`、`syncing`、`identity_same`、`merged`、`failed`。
- 登录事件、页面启动和 Socket 恢复后会自动尝试同步；失败使用指数退避重试，Hook 暴露 `retryFavoritesSync()` 供界面提供手动重试入口。
- 服务端新增 `/api/account/favorites/sync`，只接受当前账户会话和登录前签名游客交接凭证；目标身份由服务端 Cookie 决定，不接受任意游客 userId。
- 同步失败保留本地缓存和状态，Hook 提供联网自动重试、指数退避和 `retryFavoritesSync()` 手动入口。

## 上线前补充检查

- 使用两个浏览器或设备登录同一账户，确认收藏集合一致。
- 检查重复收藏、重复取消的幂等结果。
- 让账户会话失效后确认收藏读写被拒绝，重新登录后可恢复。
- 使用抓包或测试客户端提交伪造用户字段，确认服务端忽略该字段。
- 观察收藏请求成功、失败和拒绝日志，确认不记录 Cookie、Token 或账户敏感信息。
